# Day23. AI Agent의 근거 검색 및 답변 생성 과정

## 전체 처리 흐름

**사용자 → FastAPI → PostgreSQL → Embedding → pgvector → Retriever → Context 구성 → Prompt 조립 → LLM Client → 출력 검사 → 근거 검토**

1. **사용자(User)**  
   질문이나 업무 요청을 입력한다. 예를 들어 “서버는 어디에서 실행하나요?”라고 질문한다.

2. **FastAPI**  
   사용자의 요청을 받아 처리하고, 검색 및 AI 답변 생성 과정을 연결하는 API 서버 역할을 한다.

3. **PostgreSQL**  
   기존 지식의 ID, 제목, 원문, 분류 등의 데이터를 저장하고 관리한다.

4. **Embedding**  
   `multilingual-e5-small` 모델을 사용해 문장과 질문을 각각 384차원 숫자 벡터로 변환한다. 문서는 `passage:`, 질문은 `query:` 접두어를 사용한다.

5. **pgvector**  
   PostgreSQL의 확장 기능으로, Embedding 벡터를 저장하고 벡터 사이의 거리를 계산해 유사한 자료를 검색할 수 있도록 한다.

6. **Retriever**  
   질문 벡터와 저장된 문서 벡터를 비교해 관련성이 높은 자료를 Top-k 방식으로 검색하고, 원문과 ID를 반환한다.

7. **Context 구성**  
   검색된 후보 중 질문에 실제로 필요한 자료를 검토하고 선택하여 LLM에 전달할 문맥을 구성한다.

8. **Prompt 조립**  
   시스템 지시사항, 사용자 질문, 선택한 근거 자료 등을 하나의 프롬프트로 구성한다.

9. **LLM Client**  
   조립된 프롬프트를 LLM API에 전달하고, 모델이 근거 자료를 바탕으로 답변을 생성하도록 요청한다.

10. **출력 검사**  
    생성된 답변의 형식, 필수 항목, 출처 ID 등이 정해진 규칙과 일치하는지 검증한다.

11. **근거 검토**  
    최종 답변의 내용이 실제 원문 자료에 의해 뒷받침되는지 확인하고, 근거가 부족하거나 잘못된 답변은 걸러낸다.

## 전체 과정의 핵심

사용자의 질문을 벡터로 변환해 PostgreSQL에서 관련 지식을 검색하고, 검색된 근거를 LLM에 전달하여 답변을 생성한 뒤, 출력 형식과 원문 근거를 검증하는 과정이다.

## 처리 단계의 구분

- **오늘 새롭게 배우는 검색 기능:** Embedding → pgvector → Retriever
- **기존 기능 재사용 및 후속 연결:** FastAPI → Context 구성 → Prompt 조립 → LLM Client → 출력 검사 → 근거 검토

> **참고:** PostgreSQL은 원문과 메타데이터를 관리하고, Embedding은 Python에서 수행한다. pgvector는 PostgreSQL에 추가되는 벡터 검색 기능이다. 문서 벡터는 사전에 생성해 저장하고, 사용자 질문은 요청이 들어올 때 변환한다.

> **범위:** 위 순서는 전체 시스템의 기능 관계를 나타낸다. Day23의 필수 산출물은 검색 모듈을 통해 지식 ID와 원문 후보를 찾는 단계까지이며, 검색 결과를 Prompt에 넣어 LLM 답변을 생성하고 검증하는 연결은 후속 RAG 과정에서 이어진다.
